# 展开掉帧排查记录

日期：2026-10-23。代码检查基线：`ccd845f`。

## 结论

已复现首次展开和间歇性的展开卡顿。当前最明确的瓶颈在 **WebView2 GPU 进程的栅格化与合成路径**，并非已经发现了一个耗时的 React 点击处理函数。

首次完整绘制的成本明显高于连续展开；现有宽高、圆角、阴影和滤镜动画又持续产生绘制工作。两者叠加，是目前对症状最有证据支持的解释。单独删除 `blur`，或单独跳过原生窗口同步，都不能消除首次卡顿。

闲置 25 秒后的测试也出现了较长帧间隔，但样本不足以证明某个固定闲置阈值，更不能据此认定是 WebView2 休眠、缓存回收或显卡节能。代码中未找到主动挂起 WebView2 的逻辑。

首次未开启 tracing 的观察还记录到 `236.3 ms` 的帧间隔，未发现对应 JavaScript Long Task。

在包含四轮展开/折叠的 tracing 中，单个 JavaScript `FunctionCall` 最长约 `4.24 ms`、`Layout` 最长约 `0.83 ms`，而 GPU 进程的 `SkiaOutputSurfaceImplOnGpu::FinishPaintRenderPass` 最长约 `85.47 ms`，ANGLE 工作线程任务最长约 `73.76 ms`。新进程首次展开的另一条轨迹中，`RendererRasterWorker` 达到约 `177.69 ms`。

闲置后 `54.4 ms` 的样本中，GPU 进程的 `RendererRasterWorker` 达到约 `31.95 ms`，同次 `set_island_interaction` IPC 约 `10.9 ms`，没有 JavaScript Long Task。这使图形渲染链路成为比点击业务逻辑更明确的排查方向。GPU 进程事件的耗时包含 CPU、驱动及等待，并不能直接换算成显卡硬件占用。

## 对应实现

### 1. 展开路径持续改变需要重绘的属性

`src/App.css`：

- `.island` 同时过渡 `width`、`height`、`border-radius`、`transform`，前四项持续 560 毫秒，还过渡背景和阴影。
- `.island__expanded` 从 `filter: blur(6px)` 过渡到 `none`；折叠内容也有 `blur(4px)` 过渡。
- 液态玻璃外层使用背景模糊，光斑使用 `blur(20px)`，同时包含多层阴影、渐变与混合效果。
- 内容通过 `inset: 0` 跟随外壳尺寸变化。改变外壳宽高时，内部也参与布局和绘制。

这不表示布局计算本身就是主要耗时；本次轨迹中更大的停顿发生在后续栅格化与合成阶段。`will-change: width, height` 也不会自动把这些动画变成只修改合成纹理的动画。

冷启动对照中，关闭滤镜仍会停顿；同时关闭阴影和滤镜后，800 毫秒内采集到的回调数从默认样式的 36–39 个提高到 92 个，但最大间隔仍有 `115.1 ms`。进一步简化尺寸动画后也仍有一次明显首次停顿。这说明需同时关注首次资源准备及持续重绘，不能把某个 CSS 属性视为已经证明的唯一根因。

### 2. 每次开合都有不必要的原生窗口操作

`src/App.tsx` 中，模式变化触发 `syncNativeInteraction`，调用 `set_island_interaction`。

`src-tauri/src/lib.rs` 中，该命令每次都：

1. 调用 `apply_stage_geometry`，设置窗口尺寸并查询显示器；即使目标位置相同，也调用 `set_position`。
2. 调用 `apply_glass_material`，清除 Acrylic，再调用 `SetWindowRgn(..., true)` 请求重绘；即使当前已经是 CSS 玻璃回退模式，也重复执行。

默认场景下原生舞台仍是 `820 × 460`，普通开合主要只需更新点击穿透所用的状态。上述重复操作可以独立优化。本次常见 IPC 耗时约 `6–23 ms`，也出现过 `67.2 ms` 的样本；但这是端到端耗时，不能直接当成渲染线程阻塞时长。绕过此命令后卡顿仍存在，因此不能只修这里就宣布解决。

### 3. 后台轮询存在额外开销，但未证明是主因

- Agent 状态每 200 毫秒查询一次；`get_agent_status` 同步访问状态及标记文件，前端每次直接 `setAgentStatus(snapshot)`。
- 音量每 500 毫秒查询一次，静音或状态不变时也可能创建新的媒体状态对象。
- 这些更新可能带动 `IslandApp` 及其内容重新渲染，值得去除无效更新。
- 媒体原生查询已使用 `spawn_blocking`。本次严重停顿没有对应 JavaScript Long Task，因此不能把轮询或媒体查询当作已经证实的主因。

## 后续优化顺序

1. **先处理渲染路径**：让展开内容尽早拥有稳定的布局尺寸，减少外壳形变期间反复栅格化；评估把动态模糊及阴影改为成本较低的进场表现，同时保留静态玻璃外观。
2. **单独验证首次绘制准备**：研究可控的启动准备或图层复用，并重新测量首次展开。仅将内容以 `opacity: 0` 挂在 DOM 中，不能假定浏览器已经完成实际绘制。
3. **避免原生重复刷新**：普通开合更新交互状态；尺寸、位置、材质确实改变时才执行相应系统调用。保留边缘收起、拖动、多屏/DPI 变化和托盘恢复所需的路径。
4. **减少轮询造成的无效渲染**：去重未改变的状态，并评估将状态文件读取移出同步命令；保持 Agent 状态响应能力。

每一项都应重新比较首次、连续和闲置后的展开，不以一次流畅采样作为验收依据。本轮是原因排查，没有修改应用代码，也未宣称修复完成。
